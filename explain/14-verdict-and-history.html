Twin verdicts and peer history

What happens after two nodes answer the same marked pair differently: who may referee, how the signed verdict reaches every node it concerns, how each node counts verdicts about its peers (counts, never a score), and the operator's opt-in rule to stop routing to a peer. Every line is checked against the capsules plugin at release v0.1.4, and the code that is not released yet is marked as such.

1What it is

When a client marks two requests as one pair and the two nodes that served them give different answers, the node that asked can have a third node re-answer the request and sign a verdict naming the twin it does not agree with.

Each node the verdict concerns checks the referee's signature and seals its own record of it, and the node that asked counts verdicts about each peer in four plain counts, kept on its own disk.

An operator can opt in to one rule on top of those counts: after N contradictions within D days, ask the host to stop routing to that peer, which the host does only if its own operator allowed it.

2Design choices

Chosen: a pair exists only when a client marks it (x-mesh-twin-bracket); the host never adds a second request.
Rejected: the host sampling a share of requests and sending each to a second node, as the September deck showed (“about 1 in 50”). No such rate exists in the code. (capsules docs/TWIN-REFEREE-SELECTION.md §1; crates/evidence-plugin/src/referee/live.rs)
Chosen: twins that name different weights get no verdict at all (weights_mismatch); that pair is not comparable and nothing counts against either twin.
Rejected: marking the node that served other weights as contradicted, as the deck did. A weights claim is the node's own word in its signed record; a verdict rules only on words. (crates/evidence-plugin/src/referee/verdict.rs)
Chosen: referee eligibility is five yes/no rules over this node's own verified records, two tiers (with a corroboration for that model, then without), a random pick within the tier, and the tier sealed in the verdict.
Rejected: ranking candidates by merit, weighting, or any combined number. (TWIN-REFEREE-SELECTION.md §2, §3, §5)
Chosen: the verdict is a signed record held beside each node's log, and each node seals its own adjudication_issued or adjudication_received record citing it; a refused delivery is sealed by the node that tried to deliver it.
Rejected: one shared copy, or a delivery that leaves no trace when refused. (crates/evidence-plugin/src/adjudication_records.rs, referee/hold.rs)
Chosen: four counts per peer and model (corroborated, contradicted, inconclusive, not comparable), each a list of verdict ids the page can open; a received verdict counts only if this node asked that referee about that exact pair, and once per referee and pair.
Rejected: a score, a blended number, or counting any verdict that arrives: a signature says who signed, not that anyone asked, so any node with a key could otherwise mint verdicts about a peer. (crates/evidence-plugin/src/verdict_counts.rs)
Chosen: the stop-routing rule is off unless the operator sets N; with N of 2 or more, one referee alone can add at most N−1 contradictions; the rule asks the host over the plugin protocol, and the host refuses unless its operator set allow_peer_blocks = true for this plugin.
Rejected: the plugin routing anything itself, or calling the console's operator route to block a peer (the plugin did that before 0.1.3). (crates/evidence-plugin/src/routing_rule.rs; CHANGELOG.md 0.1.3)
Chosen: by default the node sends nothing to a peer on its own (it still answers a peer that asks for a record): the referee (adjudicate_differing_twins) and verdict delivery (share_adjudications) are both off until the operator turns them on, and the referee also needs record push (share_record_at_completion, off by default and symmetric) on both twins, since it is asked only once both pushed halves are held.
Rejected: the referee on by default, as the deck planned. Asking a referee sends the twins' prompt to a third node, so it needs an explicit switch. (docs/SHARING-POLICY.md; CHANGELOG.md 0.1.3)

3What it shows / what it does not

Shows

  • That the referee's key signed a ruling on one named pair of halves, at the tier it was asked from; a verdict with an altered tier fails verification.
  • For a node that seals adjudication_received: that it checked the referee's signature under the key it holds for that referee (announced by the referee's host, or set by the operator in CAPSULES_PEER_KEYS) before recording the verdict.
  • On the asking node: how many verified verdicts about each peer fall in each of four buckets, per model, with every verdict listed by id.
  • For a rule block: the rule's name and a commitment to each verdict it cited, sealed by the node that asked for the block.

Does not show

  • That an answer was right. A verdict says which twin's words the referee's own re-answer matched; the referee can be wrong too.
  • That a twin really loaded the model or weights it names: both are the node's own word in its record. Hardware evidence is the route beyond that; v0.1.4's referee flow does not use it.
  • Anything about pairs no client marked, about pairs whose twins named different weights, or about a node's future answers.
  • Anything to other nodes: the counts are this node's own and are never sent. (A peer can ask for history_card/1, a different thing: a derivation of the node's checkpoint history, with consistency proofs.)
  • A live run: v0.1.4 says a referee verdict on live hosts “is covered by tests only” (CHANGELOG 0.1.4).

4Example

A case from the plugin's referee parity corpus: node R holds three verdicts about three twin pairs served by node-a and node-b for one model, from three different referees, each one R asked for. The operator set N = 3 contradictions within 7 days. One of the three input records, then the answer the rules give.

FieldTypeMeaning
adjudication_receivedobjectThe block of R's own record of a verdict it verified: sealed only after the referee's signature checked under the key R holds for that referee.
half_node_ids[string, string]The two twins the verdict judges.
halves[hex, hex]The twins' served records, by capsule_id; with the referee they form the pair key that counts once.
model_hashhexThe model the twins named. Counts, the bar window and the referee tiers are all per model.
received_atRFC 3339When R recorded the verdict (to the minute). Windows run from this time, never from a time the referee wrote.
referee_node_idstringWho signed. A verdict whose referee is one of the twins counts nowhere.
verdictstringcontradicted:node-a: the referee's answer did not agree with node-a's. It counts as contradicted for node-a and corroborated for node-b.
verdict_capsule_idhexThe signed verdict this record cites; each count lists these ids.
countsobjectPer peer, per model, the four buckets, zeros included. Never sent to anyone.
outcomesarrayblocked: the host took the block of node-a; the three cited verdicts never count toward the rule again.
host.peer_blocksboolThe host offers the stop-routing path. Without it the outcome is no_host_hook and no verdict is spent.

The same corpus pins the edges: N−1 contradictions do not fire; four contradictions from one referee never reach three; a contradiction seven days and one second old is outside a seven-day window; after the operator undoes a block, only new contradictions fire it again.

6Specs

  • Internet-Draft draft-mih-scitt-agent-action-capsule-05 — the record envelope each half, verdict and node's record of it is sealed in; the adjudication fields inside it are the plugin's own.
  • Internet-Draft draft-mih-agent-evidence-request-00 — how a peer asks a node for records or its history_card/1; the verdict counts are not among the answers.
  • Internet-Draft draft-mih-scitt-checkpointed-local-log-02 — the node's own log that each sealed record joins.
  • RFC RFC 9052 — COSE: the COSE_Sign1 signature on each record and verdict.
  • RFC RFC 3339 — the timestamps the windows are measured from.
  • Code Mesh-LLM/capsules v0.1.4 — the plugin, the referee parity corpus and the docs cited above.
  • Code Mesh-LLM/mesh-llm#2459 — the proposed move of the plugin into the mesh-llm workspace (closed unmerged).

COSE and deterministic encoding

A signature over a digest checks only if the verifier hashes the same bytes the signer hashed, so a structured record must turn into exactly one byte string.

1What it is

A COSE_Sign1 (RFC 9052) is a CBOR structure holding a protected header, an unprotected header, a payload, and one signature computed over the encoded protected header and the payload.

A signature over a digest can be checked only by hashing exactly the bytes the signer hashed, so two implementations that rebuild those bytes from the same structured record must encode it the same way.

JSON records here use the JSON Canonicalization Scheme (JCS, RFC 8785), and for CBOR content the COSE deterministic encodings Internet-Draft in preparation lets a COSE Hash Envelope name the deterministic encoding that was applied.

2Design choices

Chosen: the Producer Envelope's payload is the raw 32 bytes of capsule_id; the protected header holds exactly alg -8 (Ed25519), content type application/agent-action-capsule-id, and kid (the raw 32-byte public key); the unprotected header is empty.
Rejected: signing hex text or the Capsule JSON. The envelope signs the stable identity, so the Capsule needs no re-serialization at verify time. (draft-mih-scitt-agent-action-capsule-05 §3.1)
Chosen: registration in a transparency log uses a separate SCITT Signed Statement over the same raw capsule_id, with CWT iss and sub in the protected header.
Rejected: treating the bare envelope as a SCITT Signed Statement, which RFC 9943 requires to carry CWT iss and sub; the three-entry envelope header has neither. (draft-mih-scitt-agent-action-capsule-05 §3.3)
Chosen: plain JCS, declared in the record (canonicalization_id: "jcs") and checked before any digest is computed; null, empty arrays, and empty objects take part.
Rejected: a normalization pass that drops null or empty members (the withdrawn jcs-n), and any undeclared or unknown construction; these fail closed. (draft-mih-scitt-agent-action-capsule-05 §2)
Chosen: no floating-point values in digest-bearing material; integers outside the IEEE-754 safe range are decimal strings.
Rejected: JSON floats. JCS fixes one output per double, but two parsers can round the same literal to different doubles, and then no canonicalization helps. (draft-mih-scitt-agent-action-capsule-05 §2; draft-mih-sokolov-scitt-payload-binding-06 §13.3)
Chosen: for CBOR, a protected Hash Envelope header parameter, payload-preimage-encoding, whose value comes from a small registry; its initial entry is core-deterministic (RFC 8949 §4.2.1).
Rejected: a media-type parameter on preimage-content-type (259). application/cbor defines no parameters, so one would be needed per media type, and a CoAP Content-Format number per pairing. (COSE deterministic encodings, Introduction)
Chosen: a verifier that holds only the decoded value encodes it with the named encoding; if the parameter is absent or unknown, it reports the content binding as unverified.
Rejected: guessing the encoding from the content type or the shape of the value. A guess cannot tell a modified value from one encoded under a different rule. (COSE deterministic encodings, Verifying the Content Binding)

3What it shows / what it does not

Shows

  • That two independent implementations derive the same bytes, and so the same digest, from the same record when both apply the declared encoding.
  • Which key signed the 32-byte identity: the envelope signature verifies under the public key in kid.
  • Which encoding produced a Hash Envelope preimage, when payload-preimage-encoding is present.
  • That a digest mismatch under a declared encoding is not an encoder disagreement: the value differs, whether by edit or by a parser that read it differently (see the next column).

Does not show

  • Unicode equivalence. JCS does not normalize Unicode, so an NFC key and its NFD spelling are different records with different digests.
  • That a parser kept the value exactly. Decoding into native types can lose distinctions such as integer versus float, and then re-encoding cannot reproduce the preimage.
  • That the signing key is authorized for the operator; that is the caller's policy.
  • Anything when the verifier has neither the preimage nor the encoding: that case is unverified, never verified and never failed.
  • Secrecy. A deterministic digest is stable, so it is linkable wherever the content recurs, and low-entropy content can be guessed.

4Example

A conformance vector whose object keys sort differently under UTF-16 code units (what JCS requires) and under code points. The input carries the keys in JCS order; the expected result gives the canonical preimage and a recomputed capsule_id equal to the carried one.

input.json
{
  "action_id": "canonical-key-sort-utf16-vs-codepoint",
  …
  "canonicalization_id": "jcs",
  "capsule_id": "9d07be6c8b0cb9efafd089ee02a2e06846854ee70c3c0f56e88925c1d2cf5dde",
  …
  "extension": {
    "canonical_test_value": {
      "😀": "hi",
      "Ｚ": "wide"
    }
  },
  "format_version": "4",
  …
}

expected.json
{
  "canonical_preimages": {
    "capsule_id": "{\"action_id\":\"canonical-key-sort-utf16-vs-codepoint\",…,\"extension\":{\"canonical_test_value\":{\"😀\":\"hi\",\"Ｚ\":\"wide\"}},\"format_version\":\"4\",…}"
  },
  "capsule_id_recomputed": "9d07be6c8b0cb9efafd089ee02a2e06846854ee70c3c0f56e88925c1d2cf5dde",
  …
  "findings": [],

5Specs

  • RFC RFC 9052 — CBOR Object Signing and Encryption (COSE): COSE_Sign1.
  • RFC RFC 8785 — JSON Canonicalization Scheme (JCS).
  • RFC RFC 9995 — COSE Hash Envelope: signs the digest of a preimage held elsewhere.
  • In preparation COSE deterministic encodings (Internet-Draft in preparation) — the payload-preimage-encoding parameter and a registry of deterministic encodings.
  • Internet-Draft draft-mih-scitt-agent-action-capsule-05 — the Producer Envelope wire profile and the format-4 JCS rules.
  • Internet-Draft draft-mih-sokolov-scitt-payload-binding-06 — how a Signed Statement declares its canonicalization (page 04).
  • Code action-state-group/agent-action-capsule — canonicalization edge-case vectors under vectors/capsule/.

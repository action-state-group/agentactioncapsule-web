One model split across peers

When one model is split across several Mesh-LLM nodes, each node runs a slice of its layers. The same record pattern then applies one level down: each stage seals what crossed its hand-offs, and the coordinator's record of the request accounts for every stage.

Status: designed and built in the plugin, not running. The capsules plugin (v0.1.4, and main @ efcada74026a2e18b9e62d77432888a31bbe9de4) contains the stage record, the coordinator's receipt naming it and the requester's check, all tested against fixture events. No host emits the per-stage events the plugin would need: upstream Mesh-LLM main @ 60697c61755b7280c22d3ab9d9bcf5b663e8ae3b broadcasts three host event channels to plugins (openai.exchange.v1, payment.lifecycle.v1, routing.choice.v1) and no stage channel. Nothing on this page has run on a live split.

1What it is

Mesh-LLM can split one model across several nodes: a coordinator runs the opening slice of layers and hands activations on to other nodes, each running the next slice.

The stage-record design turns each coordinator-to-stage pair into an exchange of its own: each stage seals a record of its slice and of the exact bytes that crossed its hand-offs, as digests, and the coordinator's record of the request cites its own record of each stage exchange and names each stage's record by digest in its receipt.

A requester holding those records can check, offline and without contacting any stage, whether both ends of every hand-off committed to the same bytes, and see a missing record as a gap rather than as agreement.

2Design choices

Chosen: nested exchanges: each coordinator-to-stage pair is an ordinary two-sided exchange; the coordinator's main record cites its own record of each stage exchange (split_stage), and its receipt names each stage's record by digest.
Rejected: a new composite record kind holding the whole split; sequence numbers, chaining, record push and pairwise citation would all have to be rebuilt. (capsules design, §5 and Q-D1)
Chosen: hash the frame bytes as the sender wrote them and as the receiver read them off the stream, before any parse.
Rejected: hashing the parsed message or the tensors; the host's codec decodes each activation on read and re-encodes it, so the parsed message is not the bytes that crossed the hop. (capsules design, §2.5)
Chosen: each lane's running digest starts from the coordinator, run, request, hop index and lane (forward, reply, direct return).
Rejected: a plain hash over the frames; a record from one hop could then be replayed as another hop's, and forward and reply frames could be mixed. (capsules design, §4.2; vector replayed_at_other_hop_index)
Chosen: a stage record that did not arrive, or a required lane empty on both ends, reads gap; the request's terminal_state is always shown beside the hand-offs.
Rejected: reading absence or two empty lanes as agreement, or agreement as completion; a request that stopped early can have both neighbours agree on a truncated stream. (capsules design, §7.2; vector stopped_early_agrees_on_truncated_stream)
Chosen: stages are never told the end requester, and the record leaves out the session id.
Rejected: carrying the session id, which stays stable across a session and would link one party's requests over time in any record shown to others. (capsules design, §4.3 and Q-D4)
Chosen: the host emits one event per stage per request, best-effort, and serving never waits on it; with no plugin declaring the channel, nothing is hashed.
Rejected: the plugin tapping the stage stream itself; split serving has no per-request hook, and the digest must sit below the codec's parse, which only the host can reach. (capsules design, §8)

3What it shows / what it does not

Shows

  • Which signing key claims which slice of the request: layer range and package id, per request, signed.
  • For each hop and lane, whether both ends committed to the same bytes: agree, break, gap, malformed or not_applicable.
  • One end misreporting, or a hand-off altered in transit, as a break on that hop, without disclosing any activation.
  • A withheld or late stage record as absent and a gap, never as agreement.
  • Whether the coordinator's assignment and the stage's own record name the same slice (disagrees when they do not).
  • Two different records sealed for one stage of one request, as conflict.

Does not show

  • That any stage computed its slice correctly; equal digests show both ends saw the same bytes, not that the output is the right function of the input.
  • Collusion: two neighbouring stages can report matching digests for anything, and a stage that alters its own output and reports it consistently is not caught.
  • That the stages are independent: a coordinator can place every stage on keys it controls.
  • That a stage loaded the weights it names; no per-slice weights digest exists, so package id and layer range are a signed claim.
  • Which end is wrong in a break.
  • Who operates a stage's key; the requester's check does not yet link a stage key to the assigned node.

6Specs

No Internet-Draft defines stage records yet; the record shape and the hop digest are the plugin's design document. The record itself is an ordinary capsule under these specs.

  • Internet-Draft draft-mih-scitt-agent-action-capsule-05 — the record each stage seals; references[] with citation_purpose (counterparty_half is defined there; split_stage is the plugin's provisional value); extension points live in the capsule JSON (§Extensibility), where the x-mesh-stage-v1 block sits.
  • Internet-Draft draft-mih-agent-bilateral-attestation-02 — related: each party records only its own side of a cross-party exchange; the coordinator's stage-exchange record cites the stage's own record with counterparty_half (one way; the stage does not cite back), without this draft's acknowledgment step.
  • Internet-Draft draft-mih-scitt-checkpointed-local-log-02 — the local log each record is appended to, and the checkpoint and inclusion proof a pushed bundle carries.
  • RFC RFC 9052 — COSE; each record's signature is a COSE_Sign1.
  • RFC RFC 8785 — JSON Canonicalization Scheme (JCS), the canonical form under each capsule_id.
  • Design Mesh-LLM/capsules: DESIGN-split-stage-records.md — the stage record, the hop digest, delivery, the console and the host ask.
  • Code Mesh-LLM/capsules — the plugin, its split-stage code and vectors.
  • Code Mesh-LLM/mesh-llm — the host and its split runtime; the per-stage event would be added here.

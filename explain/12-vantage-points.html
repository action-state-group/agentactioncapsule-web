Who can check what: three vantage points

The same records, checked from three places: your own node, the other party to the exchange, and anyone holding the evidence file. Each place adds a party who can check without trusting the one before, and each check is reported on its own, with what it does not show.

1What it is

A vantage point is a place a record is checked from: the node that sealed it, the other party to the same exchange, or a relying party who was in neither seat.

Each one holds different material (its own log; the other side's half with its proof; a file with no account behind it), so each can run a different set of checks.

Every check says what it shows and what it does not, and none of them, at any distance, says whether an answer was right.

2Design choices

Chosen: each check is a separate, independent link; a verifier stops at the level it needs, and each link states what it does not cover.
Rejected: one combined trust value; it would hide which check failed and round a gap away. (capsules docs/VERIFICATION-CHAIN.md: "Each link is independent" under "The whole chain, as one offline check"; "History is evidence, not a score" in the closing list of what the chain leaves open)
Chosen: the receiver looks up its own record of a pushed half by the half's request fingerprint. A fingerprint is not unique (one prompt sent to several peers shares it), and a push can arrive before the receiver seals its own record, so finding no own record is never a refusal. (record_push_receive.rs step 7)
Rejected: joining by exchange_id; each node mints its own, so the two would never meet. (capsules docs/VERIFICATION-CHAIN.md, opening section, which joins the two halves for display by the shared client nonce; the request fingerprint is the receiver's lookup for its own record)
Chosen: cheap refusals before any work: a push from a sender with no announced key is refused before its record is checked, and a received half is held apart, never written into the receiver's own chain.
Rejected: storing what arrives and checking later; anyone's flood would cost the receiver work and disk, and another node's record would sit in this node's history. (record_push_receive.rs, steps 1–9 and "What is kept")
Chosen: no default witness. The operator names one or more; a receipt counts only once it checks offline under the witness's key.
Rejected: a built-in witness; one log is only as neutral as its operator, and the structural answer is more than one witness holding the same checkpoint. (witness_status.rs; VERIFICATION-CHAIN Link 7)
Chosen: a refusal is an answer: signed by the responder, binding the digest of the request and the time it was issued.
Rejected: declining by silence, which leaves nothing a requester can show later; an unanswered request is a recorded absence, kept distinct from a refusal. (draft-mih-agent-evidence-request-00, "The Signed Refusal" and "The unaccountable refusal")

3What it shows / what it does not

Shows

  • Local: this exact record has not changed since it was sealed; this node's key signed it; it is in the log under a signed checkpoint; each checkpoint this node holds extends the one before it.
  • Bilateral: the other side's half is signed under the key it announced and is in its own signed log; a server a served half names is its sender, and a model it names does not contradict my own record of the same request fingerprint, when I hold one.
  • Bilateral: a sender whose checkpoint gives another root for a size that a checkpoint I already hold signed is caught (checkpoint_equivocation).
  • Relying party: from an evidence bundle, offline: record and checkpoint signatures, coverage, each record's place in the log, disclosed text against its digest; with a witness named, that the checkpoint existed outside the node by a time.
  • Relying party: which key signed a verdict, and which key signed a refusal, when one was given.

Does not show

  • Local: that the content is true, or that the node keeps only this one history; that needs someone outside it.
  • Bilateral: which side is right when the two differ, or that the two sides did not collude.
  • Bilateral: who a key belongs to; the key is node-generated, so it shows continuity, not identity.
  • Relying party: that a key is one they already trust: the signatures verify under keys the file itself carries.
  • Relying party: that every event was logged, or that the witness is honest on its own; one witness is only as neutral as its operator.
  • Relying party: the receiver-side checks of the bilateral ring, which are not in the bundle; and, for a mesh node's records, the bundle verifier is not joined yet.
  • Any ring: who withheld a record by silence; that is a recorded absence, not a refusal.
  • Any ring: whether the answer was right for you. That is judgment, and is named as a gap, never rounded away.

5Status

Checked today against the plugin's release tag v0.1.4 (b4e24453f572b2d9fe8f2cefbd0f35a5eb54b0ad) and its main (efcada74026a2e18b9e62d77432888a31bbe9de4, eleven commits later); each plugin row's claim holds at both, though the code under some rows changed in between. The verifier rows are checked against their own repositories. live is in a release and on by default; built is in the code and tested, but off by default, pre-release only, or not yet joined end to end; designed is specified, with no checking code on this path.

6Specs

  • Internet-Draft draft-mih-scitt-agent-action-capsule-05 — the record, its capsule_id and Producer Envelope: the local ring.
  • Internet-Draft draft-mih-scitt-checkpointed-local-log-02 — append, signed checkpoints, inclusion and consistency proofs.
  • Internet-Draft draft-mih-agent-bilateral-attestation-02 — both sides' records of one exchange, and the verifier states when they differ.
  • Internet-Draft draft-mih-agent-evidence-request-00 — asking for a record; artifact, signed refusal or recorded absence.
  • Internet-Draft draft-mih-agent-evidence-layer-00 — the commitment-substrate properties (append order, inclusion, consistency, checkpoint identity).
  • Internet-Draft draft-mih-zhang-agent-disclosure-bundle-01 — carrying disclosed text that hashes to a sealed digest.
  • RFC RFC 9052 — COSE; each record and checkpoint signature.
  • RFC RFC 9942 — COSE Receipts; a witness's receipt for a checkpoint.
  • RFC RFC 9943 — SCITT architecture; a Transparency Service as the witness.
  • RFC RFC 8785 — JSON Canonicalization Scheme, the bytes under each capsule_id.
  • Code Mesh-LLM/capsules — the plugin: sealing, record push and its receive checks, witness status.
  • Code action-state-group/capsule-cli — capsulectl verify --bundle and the book verbs.

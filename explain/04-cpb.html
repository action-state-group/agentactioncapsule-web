Canonicalization-declared payload binding

A signed digest of structured content is checkable only if the verifier knows how the content was turned into bytes, so the construction is declared by name and never guessed.

1What it is

CPB, the working short name of draft-mih-sokolov-scitt-payload-binding-06, defines how a SCITT Signed Statement declares the construction behind a digest it carries: the canonicalization, the hash function, and the output representation.

Each construction has a registered name, such as jcs or as-transmitted, and a payload profile declares exactly one, so a verifier recomputes the digest the same way the producer did instead of guessing.

CPB defines no payload format and no payload meaning; it defines the declarations, the registry of names, and how producers and verifiers compute and compare the digests.

2Design choices

Chosen: declare, never infer. A payload class declares exactly one registered canonicalization algorithm.
Rejected: guessing from the payload's shape, or treating Hash Envelope label 258 as the canonicalization; 258 selects only the hash function. (Draft §4, §6.2)
Chosen: a registry of immutable names, each fixing pre-image construction, hash, and output representation together; new behavior means a new name.
Rejected: redefining an existing name. jcs-n was withdrawn, not changed: its token stays bound, it cannot be newly declared, and older records are checked only with proof of pre-cutoff vintage. (Draft §4, §4.2, §14.1)
Chosen: in Hash Envelope mode the COSE payload is the raw digest octets, and representations (raw 32 bytes, bare hex, prefixed text) are declared and never silently converted.
Rejected: carrying the hex text, or letting a verifier coerce between forms; hashing a raw digest and hashing its hex text give different results. (Draft §5.1, §6.2, §7.1)
Chosen: the derived identifier removes the profile's declared exclusion set; the Hash Envelope binding covers the complete content and is checked separately.
Rejected: assuming the Hash Envelope payload is the raw form of the derived identifier, even when both use the same algorithm. (Draft §5, §6.2)
Chosen: as-transmitted for bytes a container already fixes, named by a cited production such as RFC 9052 §4.4 ToBeSigned.
Rejected: an uncited description such as "the payload bytes", or re-canonicalizing bytes a signature already fixed. (Draft §4.4)
Chosen: two digests are compared only under the same established digest context.
Rejected: treating equal-looking hex as a match; values computed under different contexts can coincide. (Draft §8.1)

3What it shows / what it does not

Shows

  • That the content a verifier holds reproduces the signed digest under the declared construction.
  • Which construction was used, by registered name, so independent verifiers recompute the same bytes.
  • Whether a digest is raw octets or text, so a leaf or comparison uses the right form.
  • That a mismatch under the declared construction is not a serializer disagreement: the value differs, whether by edit or by a parser that rounded a number differently (Draft §12.3).

Does not show

  • Anything about content the verifier does not hold. Without it, the signature can be checked but the content binding is not verified (Draft §6.2).
  • That the signer was authorized. A valid signature is Signature-Valid; accepting the key for the issuer is the verifier's policy (Draft §3).
  • What the payload means. Payload format and semantics belong to the payload profile.
  • Agreement on floats when two parsers round the same literal differently; a profile may require exact decimal strings (Draft §12.3).
  • Confidentiality of low-entropy fields: a bare digest of a guessable value can be reversed (Draft §12.2).

4Example

The smallest vector for the active jcs algorithm. It keeps the null, empty-array, and empty-object members, which is what separates plain jcs from the withdrawn jcs-n.

idstringVector identifier.
algorithmstringThe declared registered name: plain RFC 8785 JCS, no normalization pass.

5Specs

  • Internet-Draft draft-mih-sokolov-scitt-payload-binding-06 — the declarations, the Canonicalization Algorithm Registry, and the verifier rules.
  • RFC RFC 8785 — JSON Canonicalization Scheme (JCS), the construction jcs names.
  • RFC RFC 9995 — COSE Hash Envelope, used in CPB's Hash Envelope mode.
  • RFC RFC 9052 — COSE; every CPB Signed Statement is a tagged COSE_Sign1.
  • RFC RFC 9943 — SCITT architecture: Signed Statements, Receipts, Transparency Services.
  • Internet-Draft draft-mih-scitt-agent-action-capsule-05 — one payload profile that uses CPB and declares jcs.
  • In preparation COSE deterministic encodings (Internet-Draft in preparation) — names the deterministic CBOR encoding behind a Hash Envelope preimage.
  • Code action-state-group/scitt-payload-binding — draft source, registry, and conformance vectors.

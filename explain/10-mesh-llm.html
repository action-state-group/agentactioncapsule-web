Mesh-LLM capsules plugin

The open-source capsules plugin for Mesh-LLM (release v0.1.4) seals a signed record of every exchange a node serves or asks for, lets two nodes swap those records, and, for a pair of requests a client marked as twins, can ask a third node to referee answers that differ.

1What it is

capsules is a Mesh-LLM plugin that keeps, on each node's own disk, a signed and hash-chained record of every exchange that node serves or asks for, in the Agent Action Capsule format.

When the operators turn it on, the two sides of an exchange send each other their own sealed records, and each side checks the other's against the peer's key: one its host announced, bound to its node key, or one the operator configured.

When a client marks two requests as one pair and the two answers differ, a node can ask a third node to re-answer the request and sign a verdict on the pair.

2Design choices

Chosen: a pair exists only when a client sends the same x-mesh-twin-bracket value on two requests.
Rejected: the host sending a second request, or pairs guessed from timing or content: the host never does either. (mesh-llm docs/plugins/openai-exchange-lifecycle.md, “Client-marked pairs”; capsules docs/TWIN-REFEREE-SELECTION.md §4)
Chosen: the header is stripped before a request is forwarded to the serving node.
Rejected: passing it on, which would let a serving node know its answer is half of a pair. (mesh-llm PR 2300; openai-exchange-lifecycle.md)
Chosen: the host signs a binding of the plugin's key with its node key and carries it in gossip; a peer keeps it only if the binding verifies, and never relays it.
Rejected: operators copying each peer's key by hand, which does not scale and breaks for client nodes whose id changes on every start; and the node key signing plugin data itself. (mesh-llm PR 2299)
Chosen: when the host's announced key and the operator's CAPSULES_PEER_KEYS disagree for a peer, nothing from that peer verifies.
Rejected: picking one of the two keys. (capsules crates/evidence-plugin/src/peer_keys.rs)
Chosen: referee eligibility is a set of yes/no rules; the pick is random within a tier, and the tier is sealed in the verdict.
Rejected: ordering nodes by merit, weighting, or combining anything into a number. (capsules docs/TWIN-REFEREE-SELECTION.md §2, §3, §5)
Chosen: any difference between the two answers counts, and at most one referee call is made per pair.
Rejected: a similarity threshold, and retrying another referee after one did not answer. (capsules docs/TWIN-REFEREE-SELECTION.md §1)
Chosen: by default nothing leaves the node on its own: record push, verdict delivery and the referee are each off until the operator turns them on.
Rejected: sharing on by default. Asking a referee sends it the twins' prompt, so it needs an explicit switch. (capsules docs/SHARING-POLICY.md; CHANGELOG.md 0.1.3)

3What it shows / what it does not

Shows

  • That the holder of a given plugin key signed a record of one exchange, and that the record's bytes are unchanged (its capsule_id recomputes).
  • Where a host lists a peer's plugin key (mesh-llm PR 2299): that the peer's node key vouched for that key. capsules v0.1.4 reads such keys; it does not yet announce its own.
  • With record push on at both ends: each side holds the other's signed record of the same exchange.
  • For a pushed bundle: inclusion of the record under a checkpoint the sender signed.
  • For a refereed pair: a signed ruling on one pair of answers, which twin the referee's re-answer agrees with, and the word position where they start to differ (divergence_index).

Does not show

  • Who holds a key in the real world. The node key's binding says nothing about whether the node served honestly (PR 2299).
  • That a model claim is true. model_name_digest is a hash of the model's name, not of its weights.
  • Anything about a pair no client marked: those read “Not adjudicated” and nothing is called.
  • A node's future answers. A verdict is a ruling on one pair; nothing counts against a twin without one.
  • That the referee's prompt is the twins' prompt: the verdict records it as the requester's word (referee_prompt: requester_attested).
  • In v0.1.4, the plugin announcing its own key: it reads peers' announced keys; announcing its own “follows once a mesh-llm plugin release carries the request” (INSTALL.md).
  • A live run: host-announced keys were exercised only against a test build of the host, and a referee verdict on live hosts is covered by tests only (CHANGELOG 0.1.4).

FieldTypeMeaning
referee_key_idhexThe referee's Ed25519 public key; the fixture's signature verifies under it.
capsule_idhexSHA-256 of the record's canonical (JCS) bytes; changing any committed field changes it.
action_typestringdecide: this record is a ruling, not a served exchange.
provenancestringreferee: the node that wrote it was asked as referee.
source / capture_methodstringA comparison of twins, decided by the referee re-answering the request.
verdictstringA referee signs contradicted: + the node id its re-answer did not agree with, inconclusive, or not_comparable. (corroborated applies only when the answers agree, and then no referee is called.)
statusstringPaired with the verdict: SATISFIED, CONTRADICTED or UNKNOWN.
divergence_indexintegerThe word position at which the two answers start to differ.
prefix_digesthexDigest of the words the two answers share before they differ.
margin / margin_taustringRead and shown by the v0.1.4 web UI; written by no v0.1.4 Rust code. unverified what they mean.
twin_owner_distinctboolThe twins have different owners; a same-owner pair gets no verdict.
weights_digesthexThe weights both halves name; set only when both name the same.
half_a/b_capsule_idhexThe two twins' served records (A's and B's), pushed to the requesting node and held there.
referee_capsule_idhexThe referee's own record of its re-answer.
half_a/b_node_id, referee_node_idhexThe node ids of the two twins and the referee.
twins_request_digesthexDigest of the request both twins answered.
referee_promptstringrequester_attested: the prompt is the requester's word, not checked by the referee. The requesting node checks a supplied request against both records' request_digest.
referee_answer_digesthexDigest of the referee's own answer.
twin_bracket_idstringThe value the client sent in x-mesh-twin-bracket.
attestation_modestringself_attested: the signer's own key, with no outside vouching.
chainobjectLinks the verdict to half A's record with the relation adjudicates.
key_idhexThe plugin's own key that signed this record (here referee_key_id); on disk keys/node-key.pub.pem, not mesh-llm's node key.

5Specs

  • Internet-Draft draft-mih-scitt-agent-action-capsule-05 — the record format each node seals.
  • Internet-Draft draft-mih-scitt-checkpointed-local-log-02 — the node's checkpointed Merkle log; a pushed bundle carries a checkpoint and an inclusion proof.
  • Internet-Draft draft-mih-agent-evidence-layer-00 — why the plugin coarsens committed latency (a timing side channel).
  • RFC RFC 9052 — COSE: the COSE_Sign1 signature on each record.
  • RFC RFC 8785 — JSON Canonicalization Scheme: the bytes every digest and capsule_id covers.
  • RFC RFC 9943 — SCITT architecture: the witness an operator may name for checkpoints (none by default).
  • RFC RFC 9942 — COSE Receipts: what a named witness returns.
  • Code Mesh-LLM/capsules v0.1.4 — the plugin, its Evidence page, vectors and docs.
  • Code Mesh-LLM/mesh-llm#2299 — plugin keys bound to the node key, carried in gossip (merged).
  • Code Mesh-LLM/mesh-llm#2300 — the twin_bracket capability; the header stripped before forwarding (merged).

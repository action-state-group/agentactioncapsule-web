Canonical Payload Binding (CPB)

CPB is a small, single-purpose IETF draft that answers one question: how does a payload bind to a SCITT receipt? It defines how a payload class declares its canonical form and how any verifier resolves it — nothing more. This page covers the spec, the concrete problem it solves, and the machine-readable payload-class registry.

The spec

Every profile that seals structured content into a SCITT Signed Statement re-derives the same few moves. CPB (draft-mih-sokolov-scitt-payload-binding) defines those moves once, as a reusable binding, so a profile inherits them instead of restating the mechanics:

MoveWhat it does
Canonical formA payload class declares one canonicalization algorithm (e.g. RFC 8785 JCS over the payload) so any independent implementation reduces the same content to the same bytes.
Derived identifierA content-addressed identifier is derived from that canonical form, over a declared exclusion set — the fields (such as a self-referential identifier) that can't be inside their own digest.
Receipt bindingThe SCITT receipt is placed in the unprotected header of the Signed Statement, binding the receipt to that exact payload — so a receipt is unambiguously about this payload class and this record.
Typed referenceOne record cites another by its typed digest reference across profile boundaries. The referenced data stays where it lives; only the commitment travels, resolved through its declared payload class.

A payload class declares its canonicalization algorithm and exclusion set once, in the registry below, obtains an interoperable derived identifier, and inherits statement-to-receipt binding and typed-reference semantics without restating any of it. That is the whole of CPB: a way to declare a payload class and resolve it.

CPB is deliberately narrow. It is the binding — canonical form, identifier, receipt placement, typed reference. It is not the payload's semantics (each payload class owns those) and it is not how independently-verifiable records join into one accountable record — that model lives with the Agent Action Capsule standard.

Why it helps

Without a shared binding, "a receipt for this payload" is an assertion made about the bytes, out of band; two verifiers can disagree on which bytes a receipt actually covers, and a payload class defined only inside a closed product makes them disagree on what a value even means. CPB pins the answer: the receipt sits in the Signed Statement's unprotected header over a canonical form the payload class declared publicly, so any verifier resolves the same identifier and the same receipt-to-payload binding from the bytes alone. A receipt is unambiguously about this payload class and this record.

The never-reject invariant

CPB is built so that a verifier which hasn't updated degrades honestly instead of failing wrong. A verifier MUST treat an unregistered value as informational and MUST NOT reject a record solely because it carries a value the verifier doesn't recognize. The digest commits whatever bytes are present, so an unknown value breaks only semantic interpretation, never digest verification: an older verifier still confirms the seal and the receipt, and simply reports the unfamiliar value as uninterpreted rather than rejecting a valid record. New values can enter the vocabulary without a flag day.

Digest equality is a binding, not proof of truth or sufficiency. Native payload verification, identifier recomputation, and receipt verification stay separate results — a conforming verifier must never collapse them into one opaque boolean.

The registry

CPB keeps one machine-readable home for the whole payload-class family: a Payload Canonicalization Algorithm Registry and an Artifact Type Registry, both interim registries of record pending the corresponding IANA registries on RFC publication. Registration policy is Specification Required (RFC 8126), with a Designated Expert per entry, and entries are immutable in behavior — a behavior change registers as a new entry rather than editing history.

The Agent Action Capsule is the first registered artifact type; machine-mandate is registered as the second (owner-confirmed). The algorithm registry carries jcs (RFC 8785 JCS) and as-transmitted as registered algorithms. Proposed entries under discussion with their owners — for example the mesh-inference-exchange payload class — are tracked provisionally, in a separate provisional registry, until their vectors and pinning are complete.

Entries are owner-authored wherever possible, and how an entry is added depends on its provenance — a three-rung ladder:

RungStatusWhat it means
1 — Owner-authoredowner-confirmedthe payload class's own author or owner supplies every field and opens the PR. Highest provenance; the preferred path.
2 — Third-party-documentedthird-party-documentedsomeone other than the owner registers from publicly pinned artifacts (exact spec revision + commit), names themselves as registrant, and makes no endorsement claim on the owner's behalf. Upgrades to owner-confirmed on owner acknowledgment.
3 — Provisionalprovisionala reference resolves, but the vector set is incomplete or the specification isn't pinned precisely enough yet. Held in the provisional registry until it is.

CPB editors never fill in an owner's digest-context fields on their behalf, and a construction fully specified by a published standard (an algorithm defined by an RFC) is recorded as standards-referenced — there is no owner to acknowledge it. To add or vendor an entry, open a PR against the registry of record; the entry template and the per-registry ladder are documented alongside it.

Reporting: from a verified bundle to a page

Seams ④ Result to ⑤ View. Build: a page drawn only after the bundle verifies. Conform to: draft-mih-zhang-agent-disclosure-bundle-01.

A report is a presentation of an evidence file for one reader. The page is drawn only after the file verifies, by a module the reader's viewer selects from declared manifests, in words that live outside the evidence, so rewording or translating a report never moves an evidence identifier.

What must hold
  • Verify before you show.
  • A judgment is never rounded into evidence.
  • History is counts recomputed from sealed records, never a score.

1What it is

Reporting turns one verified evidence file into a page for one reader: verification runs once, its result is frozen, and a registry picks the one presentation module whose declared manifest matches the file.

The module builds a model from verified content only and draws it into a common shell that makes no network request and prints, as an offline file, a fragment link, an embedded view or a static rendering that runs no script; three separate depth levels are designed.

Words split two ways: what someone said, saw or approved is bound in the record as a commitment, while headings and labels live in a hash-pinned wording pack, so the same evidence can be reworded or translated without a single evidence identifier moving.

2Design choices

Chosen: verify once, in the core, before any module is chosen; build one frozen VerifiedBundleContext that every module reads.
Rejected: each view resolving the disclosures again from the raw file, where a view can read a payload the verifier classified as mismatched. (presentation contract v0 §2, §3.1; agent-action-capsule#202)
Chosen: modules are selected by declarative manifests; one module wins over another only through forbids; two specific modules that both match are an error, checked at registration and at resolution.
Rejected: an if/else chain over payload types in the viewer, where adding a page shape means editing the viewer and precedence is never written down; and breaking ties by priority or registration order. (contract §4.3–§4.5 and Appendix A; #207)
Chosen: evidentiary words (a request, an approval sentence, displayed terms) are bound by one of three mechanisms: a digest with an out-of-band opening, a sha256-jcs-nonce256 commitment, or a separately sealed text record.
Rejected: clear-text labels, statuses and reasons inside a sealed payload: changing a heading would change the evidence's identifier, and producer prose would look like a checked result. The cited counter-example is the report/v1 row model. (contract §7.1, §7.2)
Chosen: presentation words in a wording pack (aac.wording-pack/v0), one locale per pack, referenced by wording_sha256 over its exact bytes; the builder refuses a pack that does not hash to it, and a renderer falls back to the core's own labels.
Rejected: wording compiled into code, or carried in the manifest: a manifest carries no title, label or description, and an unknown member is an error. (contract §4.1, §7.3, §7.4; presentation builder v0 §2.1)
Chosen: a bundle that fails gets the refusal and its check list and nothing else; a viewer that cannot compute SHA-256 says “Unable to verify in this viewer”, never “failed”.
Rejected: a softened summary over a failed bundle, and drawing a missing browser capability as a failed check. (contract §8 I1; #226)
Chosen: a per-page Content-Security-Policy: no connections, and every script and inserted stylesheet listed by its SHA-256, so a module script the builder did not pin does not run.
Rejected: trusting a module because of its name or where it came from. The pin shows which code ran; it does not make the code correct. (contract §5.1, §9.2; #203, #214)
Chosen: a module declares its own presentation_api and runtime_min; a viewer that cannot honour them refuses the module and names it on the page.
Rejected: silently rendering a fallback in its place. (contract §3.2, I8)

3What it shows / what it does not

Shows

  • Whether the file verified, before anything else is drawn; on failure, which checks failed.
  • Which module drew the page, and that its script is the one the builder pinned (CSP hash).
  • Every extension in the file, each with its integrity and whether this viewer interpreted it; an unknown one reads “meaning not interpreted”, never hidden.
  • Evidentiary words only after their commitment recomputes; without an opening, that the text is committed and not opened.
  • The same content and verify state in every packaging supported for one file and one audience.

Does not show

  • That the records are true, or that an answer was right: that is judgment, kept on its own step (b9).
  • That a module's layout is a fair reading of the evidence: the pin shows which code ran, not that it is correct.
  • Anything from the static page by itself: it runs no script and says it is not self-verifying.
  • Anything from a picture or a text summary of the same model: those are presentation, never something a reader can check.
  • Who holds a signing key in the real world.

NameTypeMeaning
idstringThe module id, <dotted name>/v<major>. The aac. prefix is reserved for modules the contract's repository (now capsule-viewer) ships; anyone else uses their own name.
presentation_apistringThe module-to-runtime interface it is written against. A viewer that does not implement it refuses the module out loud.
runtime_minMAJOR.MINOR.PATCHThe lowest runtime version it needs; versioned independently of the id and of the interface.
trust_classenumtrusted-executable (a pinned script) or declarative (fields and a wording pack, no code).
requiresobjectBundle kind (equality), profile tokens <key>:<value>, and extensions that must be engaged.
forbidsobjectProfiles or extensions that must be absent: the only way one specific module excludes another.
audiences / formatsarraysWho the page is for ("*" for all) and which packagings the module supports.
fallback / prioritybool / intpriority only ranks a specific module above a fallback; it never settles a tie between two specific modules.
executableobjectWhere the script lives (module-slot) and its script_sha256; the page's CSP lists that digest.

The test of an open presentation layer

An outside developer, with only the open pieces, writes a module such as acme.monthly-risk-report/v1: a manifest under their own name, a script pinned by its hash, a wording pack. The builder puts it in a page that verifies offline, and nobody has to add a case to the viewer for it. Today that path exists for a pinned script: capsule-viewer's builder tests build pages from org.example.* module-slot modules, and refuse one whose interface or runtime the page cannot honour. The declarative path (no code at all) is designed, not built.

6Specs

  • Design spec Presentation Contract v0 — module interface, manifest, resolution, trust classes, text-binding rule, invariants, depth levels. In the capsule-viewer repository since agent-action-capsule #400; not an Internet-Draft.
  • Design spec Verification Display v0 — what a page states about verification: the check lists, the banner, the refusal's text. In the agent-action-capsule repository; not an Internet-Draft.
  • Design spec Presentation Builder v0 — the one builder, its three formats and the static rendering.
  • Internet-Draft draft-mih-zhang-agent-disclosure-bundle-01 — the Evidence Bundle being presented, what “verified” means for it, and its permalink codec.
  • Internet-Draft draft-mih-scitt-agent-action-capsule-05 — the records inside the bundle and their capsule_id.
  • RFC RFC 8785 — JSON Canonicalization Scheme: the form commitments are hashed in. A wording pack is hashed as its exact distributed bytes and never re-serialized before hashing; JCS is only the form a producer should distribute it in (contract §7.4).
  • Code agent-action-capsule — verify core, context, the bundle permalink codec, the verification display specification.
  • Code capsule-viewer — the shell, the builder, the registry, the built-in views, the presentation contract and the resolution vectors.

7What you need before the next step

  • Reports that are drawn only from a verified, frozen context, and a failure path that shows the refusal and nothing else.
  • Your report types written as modules with manifests under your own name, selected by the registry, never by your code inspecting the file.
  • Every word a reader may rely on bound in a record; every other word in a hash-pinned wording pack outside the evidence.
  • A page that makes no request and runs only pinned scripts, so a reader can open it offline from an email or a folder.
  • Reports are reads over sealed records, not new evidence. The next step does the same over time: history, read back from the records and fed into the next decision.

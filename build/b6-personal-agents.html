Personal agents

Seams ① Record to ⑤ View. Build: the five layers for an agent acting for one person. Conform to: the Personal-Agent History Profile v0 (Basic and Outcome levels), carried over draft-mih-agent-evidence-request-00.

The same five layers, applied to an agent that acts for one person: the host's seams, the records they produce, the person's own book, the deals those records belong to, and a History the person chooses to share. At the Basic level a History shows counts and makes no outcome claim; the Outcome level adds outcome claims, each resting on one named source.

What must hold
  • Verify before you show.
  • A judgment is never rounded into evidence.
  • History is counts the recipient can recompute from the answers, never a score.
Status, in the public repositories this page cites: none of them wires a personal agent's connectors, scheduler and approvals into a book end to end, so no row in section 5 is tagged live. Built at a SHA: tool-call and approval records (capsule-emit, released); the 14 conformance vectors for personal_history_basic/1, including a book's answer to a History request; and a Go verifier for evidence-interop/0 with a Basic level History evaluator (agent-action-capsule). Written down and merged: the History profile's Basic level, and its Outcome level (personal_history_outcome/1), which has conformance vectors and a test-side evaluator, and no responder or library implementation. Not built: a scheduler seam, and a History card display. Section 5 lists each item with its evidence.

1What it is

A personal agent acts for one person: it calls tools through connectors, waits for that person's approval on some actions, and runs scheduled tasks while nobody is watching. Each of those is a place where the host can hand an event to code that seals a signed record.

The records go into the person's own append-only book, grouped into deals (one correlation id each), and each record says whether a step the agent recorded completed or failed. The book may be one stream or several, for example one per deal; every record of one deal stays in one stream, and one History may span several streams when it is answered at one witnessed checkpoint tick, a checkpoint of the holder's, countersigned by a witness, that commits to each stream's checkpoint (profile §2, PA-14).

When the person wants to show someone what their agent recorded, they pick some deals for that one recipient, and the recipient gets a History, signed by the holder key, that counts the selected deals by state and states plainly that no outcome is established. That is the Basic level. At the Outcome level the History can also carry outcome claims, each naming one source, shown side by side (end of section 3).

2Design choices

Chosen: seal what changes the world, plus reads of sensitive data; a read-only tool call is observability, not a record.
Rejected: sealing every call; a query (MCP readOnlyHint: true, an HTTP safe method) is observability, not a consequential-action record, unless it reads sensitive data. (capsule-emit docs/whats-consequential.md, the two-signal rule; MCP readOnlyHint, HTTP safe methods)
Chosen: an approval is its own signed record, chained to the blocked record with the relation supersedes; with no such record, the action is still pending.
Rejected: marking an action approved without a chained record. (capsule-emit python/capsule_emit/approval.py: fail-closed list_pending)
Chosen: the subject of a History is the holder's signing key, not a person, a name or an account.
Rejected: naming the person; a label the holder attaches to the key is the holder's own statement and is never checked. (spec/personal-agent-history-profile-v0.md §2)
Chosen: a closed list of two record kinds for a History: step_completed and step_failed.
Rejected: any other record type, which could name an item, a category or a counterparty. (profile §3)
Chosen: a History is a recipient-specific disclosure; its identifier is the SHA-256 of the canonical (JCS) definition, which names the recipient and the selection, so two recipients get two identifiers.
Rejected: a registered derivation token sent on the wire, or presenting a History answer as the canonical answer for the deal it covers. (profile §4, §4.2)
Chosen: the holder selects deals, and the definition says completeness: not_asserted, which is the coverage kind holder_selected; a verifier shows that coverage kind, with outcomes not established, before any count.
Rejected: implying the selection is everything; a holder can leave out any deal, a valid signature on every answer never implies completeness, and a requirement that needs a complete History is never satisfied from a Basic level History. (profile §2, §4.1, §6.3 item 1, §9, PA-15; interop profile §6.7)
Chosen: counts in their own units: selected deals, and the count of each deal state; records counted separately.
Rejected: any figure that adds deals to records, combines across deals, holders or counterparties, or orders or grades them. (profile §5, §9 “No ordering”)
Chosen: before release, the holder's host byte-scans every reply for text outside the four declared fields (names, contact details, items, amounts, message text, unselected deal references).
Rejected: relying on the recipient's verifier alone, which checks the field set but cannot spot text it has never seen. (profile §4.4)

3What it shows / what it does not

Shows

  • For a connector call or approval record: that the key named in the record signed its id, and that its content matches that id (the id recomputes).
  • For a History: which deals the holder selected for this recipient.
  • When each record was committed to the holder's stream, and the event time the agent claimed, as two separate times.
  • Whether each recorded step completed or failed, as the holder's agent recorded it.
  • That one holder key answered for every selected deal, at one anchor, whether the answers name one stream or several.
  • The coverage kind, holder_selected, before any count.

Does not show

  • At the Basic level, any outcome: sale, payment, delivery, receipt or return. A recorded completed step is not a completed sale. Outcome claims are the Outcome level's, below.
  • That the selection is all of the holder's deals: the coverage kind is holder_selected, completeness not asserted (PA-15).
  • That a shared anchor is a witnessed checkpoint tick, or that it commits to the stream an answer names: at the Basic level a verifier checks only that every answer names the same anchor (PA-14).
  • That anything happened at the claimed event time; neither time is witnessed.
  • Who holds the key, or that the key's holder made the deals.
  • Record-level inclusion for a History answer: anchor_inclusion is NOT_CHECKED until the interop profile registers the material for it (PA-13).
  • That two recipients cannot link a shared deal: deal references and record digests are the same in every History (§4.5, PA-7).

The Outcome level: what it adds (designed)

The Outcome level, personal_history_outcome/1, is a History whose deals also carry outcome claims: what a named source says happened in a deal. Each claim names one predicate and exactly one source. A verifier checks each claim against its own source and shows the claims side by side, one row per claim. It never combines them into one outcome, one count or one figure, and the level defines no rate, share or figure across deals.

  • A claim that only the holder's record ties to the deal never gives met or not_met, because that record's inclusion is not checked.
  • The deal's terms are committed by digest in the holder's stream; the opening that reveals them goes only to the recipient, beside the answers.
  • The definition carries a coverage declaration of any of the three kinds (holder_selected, stream_interval, source_authoritative), so a History at this level can say more than “the holder chose these”.

6Specs

  • Internet-Draft draft-mih-agent-evidence-request-00 — the request, the correlation subject, derivation by definition digest, derivation-scoped disclosure.
  • Internet-Draft draft-mih-agent-evidence-layer-00 — the record header (record_type, epistemic_type) a History reads.
  • Internet-Draft draft-mih-scitt-agent-action-capsule-05 — the record format capsule-emit seals for tool calls and approvals.
  • Internet-Draft draft-mih-scitt-checkpointed-local-log-02 — the checkpointed log under the person's book.
  • RFC RFC 8785 — JSON Canonicalization Scheme: the bytes the derivation digest covers.
  • Profile spec/personal-agent-history-profile-v0.md — Personal-Agent History Profile v0, Basic level (informational, pre-Internet-Draft).
  • Profile spec/personal-agent-history-outcome-v0.md — its Outcome level, personal_history_outcome/1 (informational, pre-Internet-Draft).
  • Profile spec/interop-profile-v0.md — the interop profile (evidence-interop/0) whose envelope, verifier and coverage declaration (§6.7) a History uses unchanged.
  • Code action-state-group/capsule-emit python/v0.11.0 — the MCP adapter and approval records.

7What you need before the next step

  • Your host's four seams named: connector calls, approvals, scheduled tasks, and a hook that carries each to the sealer.
  • One correlation id per deal, chosen at random when the deal opens, and a mapping from your native step status to step_completed / step_failed.
  • One holder key answering every deal of a History, and a pre-release scan for text outside the four declared fields.
  • A verifier display that shows “outcomes not established” and the coverage kind holder_selected, with completeness not asserted, before any count, and never combines the counts.
  • Next, a second party: work an agent does for someone, with a counterparty who keeps its own records.

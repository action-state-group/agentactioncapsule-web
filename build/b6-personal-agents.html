Personal agents

Seams ① Record to ⑤ View. Build: the five layers for an agent acting for one person. Conform to: draft-mih-agent-evidence-request-00 (the History profile).

The same five layers, applied to an agent that acts for one person: the host's seams, the records they produce, the person's own book, the deals those records belong to, and a History the person chooses to share, which shows counts and makes no outcome claim.

What must hold
  • Verify before you show.
  • A judgment is never rounded into evidence.
  • History is counts anyone can recompute, never a score.
Status: designed, not built for a personal-agent host. None of the public repositories this page cites wires a personal agent's connectors, scheduler and approvals into a book end to end. Built at a SHA today: tool-call and approval records (capsule-emit, released), and the 12 conformance vectors for personal_history_basic/1, including a book's answer to a History request (agent-action-capsule). Written down and merged, no host code: the History profile itself. Not built: a scheduler seam, and a History card display. Section 5 lists each item with its evidence.

1What it is

A personal agent acts for one person: it calls tools through connectors, waits for that person's approval on some actions, and runs scheduled tasks while nobody is watching. Each of those is a place where the host can hand an event to code that seals a signed record.

The records go into the person's own append-only book, grouped into deals (one correlation id each), and each record says whether a step the agent recorded completed or failed.

When the person wants to show someone what their agent recorded, they pick some deals for that one recipient, and the recipient gets a History, signed by the holder key, that counts the selected deals by state and states plainly that no outcome is established.

2Design choices

Chosen: seal what changes the world, plus reads of sensitive data; a read-only tool call is observability, not a record.
Rejected: sealing every call; a query (MCP readOnlyHint: true, an HTTP safe method) is observability, not a consequential-action record, unless it reads sensitive data. (capsule-emit docs/whats-consequential.md, the two-signal rule; MCP readOnlyHint, HTTP safe methods)
Chosen: an approval is its own signed record, chained to the blocked record with the relation supersedes; with no such record, the action is still pending.
Rejected: marking an action approved without a chained record. (capsule-emit python/capsule_emit/approval.py: fail-closed list_pending)
Chosen: the subject of a History is the holder's signing key, not a person, a name or an account.
Rejected: naming the person; a label the holder attaches to the key is the holder's own statement and is never checked. (spec/personal-agent-history-profile-v0.md §2)
Chosen: a closed list of two record kinds for a History: step_completed and step_failed.
Rejected: any other record type, which could name an item, a category or a counterparty. (profile §3)
Chosen: a History is a recipient-specific disclosure; its identifier is the SHA-256 of the canonical (JCS) definition, which names the recipient and the selection, so two recipients get two identifiers.
Rejected: a registered derivation token sent on the wire, or presenting a History answer as the canonical answer for the deal it covers. (profile §4, §4.2)
Chosen: the holder selects deals, and the definition says completeness: not_asserted.
Rejected: implying the selection is everything; a holder can leave out any deal, and a verifier shows that the selection is not claimed to be complete. (profile §4.1, §9)
Chosen: counts in their own units: selected deals, and the count of each deal state; records counted separately.
Rejected: any figure that adds deals to records, combines across deals, holders or counterparties, or orders or grades them. (profile §5, §9 “No ordering”)
Chosen: before release, the holder's host byte-scans every reply for text outside the four declared fields (names, contact details, items, amounts, message text, unselected deal references).
Rejected: relying on the recipient's verifier alone, which checks the field set but cannot spot text it has never seen. (profile §4.4)

3What it shows / what it does not

Shows

  • For a connector call or approval record: that the key named in the record signed its id, and that its content matches that id (the id recomputes).
  • For a History: which deals the holder selected for this recipient.
  • When each record was committed to the holder's stream, and the event time the agent claimed, as two separate times.
  • Whether each recorded step completed or failed, as the holder's agent recorded it.
  • That one holder key answered for every selected deal, at one anchor.

Does not show

  • Any outcome: sale, payment, delivery, receipt or return. A recorded completed step is not a completed sale.
  • That the selection is all of the holder's deals.
  • That anything happened at the claimed event time; neither time is witnessed.
  • Who holds the key, or that the key's holder made the deals.
  • Record-level inclusion for a History answer: anchor_inclusion is NOT_CHECKED until the interop profile registers the material for it (PA-13).
  • That two recipients cannot link a shared deal: deal references and record digests are the same in every History (§4.5, PA-7).

FieldTypeMeaning
namestringThe level's readable name. It is not a registered token and is never sent as one.
kindstringprojection: a view over the holder's records, not the records themselves.
subject_formstringcorrelation: each request names one deal.
selectionarrayThe deal references the holder picked: sorted, no duplicates, never derived from counterparty, item, amount or message text.
readsarrayThe only record fields any answer may reveal, exactly these four.
completenessstringnot_asserted: the selection is not claimed to be every deal.
recipientstringThe one requester the holder's responder answers under this definition; any other is refused (not_authorized in the vectors).
derivationhexSHA-256 of the definition's canonical JSON; the holder key signs it in every reply, so it binds the recipient, the selection and the field set.
anchorhexThe checkpoint the whole History is answered at; one anchor for every deal.
records[].digest / leaf_indexhex / intThe record's identifier and its position in the stream. No payload, counterparty or message text.
committed_attimeWhen the holder's own stream committed the record.
event_time_claimtimeWhen the holder's agent says the step happened; a claim, shown apart from committed_at.
epistemic_typestringproducer_claim: the holder agent's own label, never shown as anyone else's corroboration.
record_typestringstep_completed or step_failed; anything else fails record_kinds.

6Specs

  • Internet-Draft draft-mih-agent-evidence-request-00 — the request, the correlation subject, derivation by definition digest, derivation-scoped disclosure.
  • Internet-Draft draft-mih-agent-evidence-layer-00 — the record header (record_type, epistemic_type) a History reads.
  • Internet-Draft draft-mih-scitt-agent-action-capsule-05 — the record format capsule-emit seals for tool calls and approvals.
  • Internet-Draft draft-mih-scitt-checkpointed-local-log-02 — the checkpointed log under the person's book.
  • RFC RFC 8785 — JSON Canonicalization Scheme: the bytes the derivation digest covers.
  • Profile spec/personal-agent-history-profile-v0.md — Personal-Agent History Profile v0 (informational, pre-Internet-Draft).
  • Profile spec/interop-profile-v0.md — the interop profile (evidence-interop/0) whose envelope and verifier a History uses unchanged.
  • Code action-state-group/capsule-emit python/v0.11.0 — the MCP adapter and approval records.

7What you need before the next step

  • Your host's four seams named: connector calls, approvals, scheduled tasks, and a hook that carries each to the sealer.
  • One correlation id per deal, chosen at random when the deal opens, and a mapping from your native step status to step_completed / step_failed.
  • One holder key answering every deal of a History, and a pre-release scan for text outside the four declared fields.
  • A verifier display that shows “outcomes not established” before any count, and never combines the counts.
  • Next, a second party: work an agent does for someone, with a counterparty who keeps its own records.

Making it portable

Evidence is portable when the format is an open spec with vectors, the code is libraries any host can link by version, and the saved file can be checked offline by a verifier that never talks to the host, an account or an operator.

1What it is

Portability is a layering rule: open specs and vectors at the bottom, libraries that pass those vectors above them, and the host-specific plugin on top, depending on the libraries by version.

What leaves the host is one file in an open format, holding the records, their signatures, a signed checkpoint and an inclusion proof for each record.

Any verifier that implements the spec checks that file offline from the file and the signer's key alone, so the evidence still checks if the host, its operator or the plugin's author goes away.

2Design choices

Chosen: the plugin links the sealing, log and check code as published crates, named by version; those crates are developed and tested in their own repositories.
Rejected: copying the library code into the plugin. (capsules README.md “Repository layout” and crates/evidence-plugin/Cargo.toml @ v0.1.4)
Chosen: the evidence-request crate is pinned exactly (=0.0.3), because “a new release may change what verifies”.
Rejected: a caret range for a crate whose new release can change a verification result. (capsules crates/evidence-plugin/Cargo.toml @ v0.1.4, comment on capsule-emit-evidence-request)
Chosen: the spec's vectors are copied into the plugin unchanged, pinned to a spec tag and its commit, listed in SHA256SUMS, and run in the plugin's tests.
Rejected: vectors generated by the implementation under test. (capsules vectors/SOURCES.md; tests/aac_canonical_vectors.rs @ v0.1.4)
Chosen: no default witness. A checkpoint is registered only with a service the operator names, and each witness is dialled at the URL given.
Rejected: a built-in service every node reports to, which would make one operator part of every check. (capsules docs/VERIFICATION-CHAIN.md Link 7; Cargo.toml comment on capsule-emit 0.0.6 @ v0.1.4)
Chosen: the evidence file is checked “offline, from the file alone. No profile and no network are used.”
Rejected: checking by asking the producer's node or a hosted service, which needs the producer to still exist. (draft-mih-zhang-agent-disclosure-bundle-00; capsule-cli README.md, verify --bundle)
Proposed (open PR): when the plugin moves into the host's own repository, the host's plugin API becomes a path dependency, and the evidence libraries stay versioned registry crates.
Rejected: git dependencies or [patch] overrides. (Mesh-LLM/mesh-llm#2459, open: “no [patch] and no git dependencies”)

3What it shows / what it does not

Shows

  • From an evidence file alone: each record's identity (its capsule_id recomputes), its producer signature, the signed checkpoint, and each record's inclusion under that checkpoint.
  • That the sealing crate computes the same capsule_id as the spec's reference for every canonical-* vector at the pinned tag.
  • Exactly which library release the plugin was built against: Cargo.lock records the version and its registry checksum.
  • That no verifier step depends on the host, the plugin's author or a hosted service still existing.

Does not show

  • Who holds the signing key in the real world: the key is node-generated and self-attested (capsules docs/VERIFICATION-CHAIN.md Link 3).
  • That an answer was right, or that every event was logged.
  • Anything from the capsules plugin's own saved files today: v0.1.4 writes mesh-ledger-exchanges-evidence/1, mesh-ledger-integrity-evidence/1 and mesh-ledger-peers-evidence/1, schemas no verifier reads.
  • Outside time: with no witness named, nothing outside the node saw the checkpoint.
  • Full coverage for the two live-run evidence-file vectors on every verifier version: records, signatures, closure and checkpoint pass, while coverage and membership depend on the agent-action-capsule version (capsule-emit test-vectors/evidence-file/README.md).
  • That two hosts write byte-identical records: only that both follow the same format and pass the same vectors.

6Specs

  • Internet-Draft draft-mih-scitt-agent-action-capsule-05 — the record format, and the vectors that pin it.
  • Internet-Draft draft-mih-zhang-agent-disclosure-bundle-00 — the evidence file (evidence-bundle/v2).
  • Internet-Draft draft-mih-scitt-checkpointed-local-log-02 — the signed checkpoint and the inclusion and consistency proofs the file carries.
  • Internet-Draft draft-mih-agent-evidence-request-00 — the protocol the pinned evidence-request crate implements.
  • RFC RFC 9052 — COSE: the COSE_Sign1 on records and checkpoints.
  • RFC RFC 8785 — JSON Canonicalization Scheme: the bytes every capsule_id covers.
  • RFC RFC 9943 — SCITT architecture: a witness the operator may name.
  • RFC RFC 9942 — COSE Receipts: what a witness returns, checked offline.
  • Code agent-action-capsule — drafts and conformance vectors.
  • Code capsule-emit · checkpointed-local-log · evidencebook · scitt-cose — the libraries.
  • Code capsule-cli · capsule-viewer — capsule-cli is a verifier; capsule-viewer draws an offline report page from capsule-emit's check. Both read the file offline.
  • Code Mesh-LLM/capsules v0.1.4 — the worked example's host plugin.

7What you need before the next step

  • Your sealing, log and check code published as libraries, and your host plugin naming them by version, with an exact pin wherever a new release could change what verifies.
  • The spec's vectors copied in unchanged, pinned to a tag, and run in your tests.
  • An export that writes the open evidence-file format, not a schema of your own, checked by at least one verifier you did not write.
  • No default service in the path: a witness only when the operator names one, and a verifier that needs nothing but the file and the signer's key.
  • A clear split between what the host must provide and what the libraries provide, so the same layers can be laid on a different host: next, a personal agent.
